# 项目运行时探测

`project` 是模板前缀，实例化时统一替换。Runtime probe 是诊断实验，不是默认测试层级，也不替代可自动回归的验证。

## 何时使用

- 行为取决于真实时钟、进程边界、网络流、文件系统、缓存、重启或并发调度
- 日志与代码已经缩小候选边界，但仍存在两个以上可区分假设
- 用户明确要求实际运行、复现或采集运行时证据

普通代码改动优先使用 `project-test-verification`；已有证据足以判断时不要为增加日志而运行实验。

## 实验设计

1. 写清假设、判定它的可观察量和停止条件
2. 记录基线，并设计正常 control、目标场景以及必要的边界、失败或恢复场景
3. 使用最小可控输入，固定版本、配置、identity、工作目录和外部依赖
4. 只增加完成判定所需的观测，不永久改变生产日志或接口
5. 重复足以区分确定性与偶发现象；无法复现时报告证据边界，不宣称问题不存在

## 最小证据

- 环境：版本、配置来源、进程或容器关系、工作目录和依赖状态
- 身份：请求、会话、任务、进程或资源 identity，以及是否复用
- 时间线：输入、关键状态变化、外部调用、取消、终态和清理时间点
- 结果：命令或入口、退出码、结构化日志、产物路径与实际外部影响
- 对照：control 与目标场景唯一变化的变量

## 授权与清理

默认只在本地或隔离环境执行可回收实验。访问生产系统、真实用户数据、凭据、付费服务，发送外部消息，或修改共享状态前必须取得用户对该影响的明确授权。实验前定义清理方式；结束后停止临时进程、释放端口与资源，并说明保留的证据位置。

## 交接

输出区分事实、推断和仍未裁定的假设。若实验得到稳定复现，把最小输入和可观察判据交给 `project-test-verification` 固化回归；需要修改生产实现时交给 `project-code-implement`，不在诊断过程中顺手扩大修复范围。
