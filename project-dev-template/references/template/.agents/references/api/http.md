# HTTP API 文档写作模板

本文定义项目 HTTP 接口的统一契约结构。其它请求/响应式协议（RPC、消息、事件回调等）也应复用“总览—通用约定—逐接口输入—成功—错误—归属”的信息结构，只替换传输层术语，不降低契约完整度。

## 写作目标

- 让调用方无需阅读实现即可构造请求、判断成功、处理失败和安全重试。
- 明确 HTTP 层只负责的校验与响应，以及业务能力、工作流和异步交付各自的 Owner。
- 同时记录当前实现、兼容边界和演化规则，避免示例成为唯一规范。

## 必答问题

1. 有哪些公开、内部和主动调用接口；它们分别面向谁？
2. 通用的鉴权、请求关联、内容类型、版本、时区、编码和响应封装是什么？
3. 每个接口是同步完成、异步接受还是流式处理；“成功”精确表示什么？
4. path、query、header、body 每个字段的类型、必填性、校验、默认值和业务语义是什么？
5. 成功的 HTTP 状态、响应 header/body、状态变化和副作用是什么？
6. 每类失败的触发条件、HTTP 状态、业务错误码、可否重试和副作用是什么？
7. 重复请求、超时、客户端断开、并发请求和乱序到达如何处理？
8. 接口由哪个 route 接入、哪个能力拥有、对应哪条数据流；字段事实源在哪里？
9. 版本升级、字段增删、弃用和兼容窗口如何表达？

## 写作约束

- 规范正文以字段表和明确语义为准；JSON、curl 或 HTTP 示例只用于说明，不能替代表格。
- 区分字段“未出现”、`null`、空字符串、空数组、零值和默认值；若等价必须明确说明。
- 对枚举、格式、长度、范围、互斥、联动和优先级规则写出确定行为，不使用“合法值”等循环描述。
- 对异步接口明确区分“请求已接受”和“业务已完成”，并说明后续结果的观察通道、identity 和终态。
- 错误必须可操作：调用方应能判断修正请求、重试、等待、重新鉴权或停止处理。
- 示例中的 token、用户数据、域名和 ID 必须是显然虚构的安全值。
- 规划中或实验性接口显式标记状态，不能与当前可用接口混在同一张无状态表中。

## 推荐章节

### 接口总览

| 状态 | 方法与路径 | 可见性 | 调用方 | 同步模型 | 用途 | 契约 Owner |
|---|---|---|---|---|---|---|
| 已实现、实验或规划 | `METHOD /path` | 公开或内部 | 角色/系统 | 同步、异步接受或流式 | 一句话结果 | 能力或协议入口链接 |

同一路径存在兼容别名时列在同一行，并说明哪个是规范名称和别名移除条件。

### 通用约定

按项目适用范围明确：

- base URL、协议版本和版本选择方式；
- 鉴权/授权方式及凭据所在 header，不写真实凭据；
- request/correlation/idempotency identity 的生成、回传和作用域；
- `Content-Type`、字符编码、日期时间、数字精度和字段命名风格；
- 通用成功封装、通用错误封装和 HTTP 状态使用原则；
- pagination、排序、过滤、限流、超时和重试 header；
- 敏感字段、日志脱敏和缓存策略。

没有全局统一约定的维度应留给逐接口章节，不要制造虚假的全局规则。

### `METHOD /resource`

每个接口独立使用本结构；将标题替换为真实方法和路径。

#### 目的与处理模型

说明调用场景、前置权限、同步/异步边界、成功含义、主要副作用和不负责的后续动作。若同一接口支持多种模式，先用判别表描述模式选择条件，不把复杂分支藏进示例。

#### Request

```http
METHOD /resource/{resource_id}?mode=example
Content-Type: application/json
Authorization: Bearer example-token
X-Request-ID: req_example_001
```

按位置分表；没有某类参数时明确写“无”，不要省略后让调用方猜测。

| 字段 | 位置 | 类型 | 必填 | 校验与默认值 | 对外语义 | 敏感性 |
|---|---|---|---|---|---|---|
| `resource_id` | path/query/header/body | string 等 | 是、否或条件必填 | 范围、格式、互斥、优先级 | 该值会改变什么 | 普通、敏感或不得记录 |

请求示例至少覆盖标准路径；若存在容易误用的条件模式，再增加一个对比示例。示例后补充无法由表格表达的整体约束，例如字段组合、幂等作用域和并发准入。

#### Success response

明确 HTTP 状态和响应 header，再给出安全示例：

```json
{
  "data": {
    "id": "resource_example"
  }
}
```

| 字段 | 类型 | 是否总出现 | 语义与来源 |
|---|---|---|---|
| `data.id` | string | 是 | 由哪个事实 Owner 生成 |

随后说明响应返回时哪些状态已经提交、哪些工作仍在异步执行、重复读取是否稳定，以及客户端从哪里观察最终结果。

#### Error response

先给通用错误结构的一个示例，再列完整可区分错误：

| HTTP 状态 | 业务错误码 | 触发条件 | 客户端动作 | 可否重试 | 已发生的副作用 |
|---|---|---|---|---|---|
| 使用真实契约 | 稳定机器码 | 精确到可判断条件 | 修正、等待、鉴权或停止 | 否、立即或退避 | 无、部分或已提交 |

同一错误码覆盖多个不同客户端动作时应拆分；不要依赖易变化的自然语言 message 做程序判断。

#### 幂等、并发与超时

说明幂等键、去重窗口、重复响应、并发冲突、服务端超时、客户端断开、重试后结果查询，以及可能出现的“请求超时但服务端已提交”。不适用时写明原因。

#### Ownership 与数据流

- route 和请求级校验由哪个入口拥有；
- 业务状态变化由哪个 [capability](../capability/) 拥有；
- 端到端数据流由哪个 [workflow](../workflow/) 维护；
- 字段 schema、生成规则或事件协议的唯一 Owner 在哪里。

这里只写链接和边界摘要，不复制能力或工作流正文。

### 兼容与演化

记录版本策略、向后兼容定义、字段新增/弃用规则、未知字段处理、枚举扩展、兼容别名和迁移窗口。破坏性变化链接 ADR 与迁移计划。

### 归属规则

列出本文拥有的 route 范围，以及由其它协议、能力或外部系统维护的接口。主动出站调用和入站接口可以放在同一文档，但必须在总览中区分方向。

## 禁止内容

- 不只写 happy path、curl 示例或实现函数名，不省略错误和异步完成语义。
- 不写真实密钥、cookie、个人数据、生产域名或可复用的认证材料。
- 不复制能力内部流程、数据库表结构或第三方服务完整手册；只维护本项目依赖的契约边界。
- 不用 HTTP 200/500 的笼统描述代替稳定业务错误，不让自然语言错误消息成为唯一判断依据。
- 不把尚未实现的接口写成当前可用，也不在没有兼容策略时静默改变字段含义。
