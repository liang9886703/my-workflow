# Capability 文档维护流程

本 reference 只在创建、拆分、迁移或评审 `.agents/references/capability/` 下的单项能力文档时读取。它负责项目内长期有效的选址、取证、同步和生命周期管理，不依赖会在模板实例化时被改名或删除的 artifact scaffold，也不重复成品文档的通用章节。

## 何时需要独立能力文档

只有同时满足下列条件时才新增文档：

- 存在可独立说明、会长期保持的结果或责任边界；
- 能指出稳定触发者、消费者以及相邻 Owner；
- 该能力拥有至少一项需要长期约束的数据、资源、公共入口、生命周期或失败收敛责任；
- 内容无法由概念、总体架构、数据、API、环境或既有能力文档更准确地拥有。

仅有一个目录、class、外部依赖、临时任务或若干相似 helper，不足以构成独立能力。此时把事实留在代码、实现 reference 或现有长期 Owner。

## Owner 与选址

1. 用一句“该能力向谁提供什么稳定结果”定义候选边界。
2. 列出它拥有和不拥有的责任，并为每项非目标指出相邻 Owner。
3. 检索概念、架构、数据、API、workflow 和已有 capability，确认正文没有现存 Owner。
4. 使用稳定业务或技术能力名命名文件，不按版本、任务、缺陷、团队或当前实现类名命名。
5. 跨多个能力的共同不变量上移到架构或数据文档；动作特有的端到端交接写入 workflow；字段级契约写入 API。

无法为一项事实找到唯一 Owner 时先调整能力划分，不通过在两个文档同时保留正文来折中。

## 事实取证

创建或修改前读取最小证据集：目标能力的公共入口和 composition root、直接调用方、相邻能力、相关 schema/配置、已有测试，以及会约束该能力的基础 reference。

将内容分成三类后再落笔：

- 已实现事实：代码、配置或测试可直接证明，且确有长期记录价值；
- 稳定设计：用户或现有设计明确要求、用于约束实现演化；
- 待决问题：证据不足或仍有多个合理方案，只记录决策条件，不写成事实。

不要用一次运行结果、局部 helper、当前装配顺序或历史报告替代长期证据。

## 新建与拆分

- 优先沿用目标项目已有 capability 文档的稳定结构；首次建设时，由外层项目模板在实例化阶段提供 artifact scaffold，生成具体能力文件后删除通用脚手架。
- 初稿先建立目标、职责/非目标、相邻 Owner 和数据/资源 ownership，再补生命周期、异常与验证要求。
- 一个文档开始拥有两个可独立演化的结果、不同生命周期或不同失败收敛方时才考虑拆分。
- 拆分时先确定新旧 Owner，再移动正文并把旧位置收敛为链接；不要复制后等待以后清理。
- 多份短文档只有共同 Owner 且经常需要同时变化时才合并；文件数量本身不是合并理由。

## 修改与同步

按变化类型检查直接入链：

| 变化 | 必查位置 |
|---|---|
| 目标、职责或非目标 | 概念、架构、相邻 capability、AGENTS 路由 |
| 公共输入输出或错误语义 | API、调用方、workflow、兼容说明 |
| 数据 Owner、共享或持久化 | data design、生产者、消费者、迁移约束 |
| 创建基数、生命周期或资源清理 | architecture、environment、实现 reference、测试要求 |
| 文件或公共入口移动 | 所有相对链接、composition root、项目实施 skill 路由 |

代码任务本身不授权修改长期 capability 文档。实现发现长期缺口时，在交付中报告候选 Owner 和影响，由独立文档任务处理。

## 评审清单

- 文档能否用单一稳定结果命名，且职责与非目标不会同时落到两个 Owner？
- 每个稳定对象、数据和资源是否说明创建、共享、identity、替换与清理责任？
- 是否把字段级 schema、完整文件树、callback 接线或局部算法误放进长期设计？
- 当前事实、目标约束和待决问题是否清楚区分？
- 修改是否同步检查了上游、下游、API、数据流、环境假设和测试要求？
- 相对链接是否有效，移动后的旧路径是否只剩必要迁移说明而非影子正文？

具体章节以目标项目已采用的能力文档结构为准。结构需要演化时，在项目文档任务中一次性更新现存能力文档和维护规则；不要保留一份没有项目事实、只供复制的长期 capability 文件。
