# 项目代码评审

`project` 是模板前缀，实例化时统一替换。本 skill 默认只读；用户明确要求同时修复时，再交给对应实施 skill 执行。

## 证据准备

1. 明确评审范围和基线，读取状态、diff、需求与当前作用域 `AGENTS.md`
2. 按变更路径读取目标代码、调用方、测试、配置、长期 reference 与 implementation reference
3. 运行能验证具体怀疑的非破坏性静态检查或测试，不用全量命令替代代码推理
4. 区分本次引入的问题、已有问题和无法从现有证据确认的风险

## 评审重点

- 可观察行为是否符合需求，成功、失败、取消和重试路径是否完整
- API、数据、配置、事件或持久化契约是否发生未声明的不兼容变化
- 对象、数据、异步任务和资源是否有正确 owner、identity、共享基数与清理责任
- 并发、幂等、迟到结果、超时、部分失败和恢复是否保持不变量
- 权限、密钥、隐私、输入校验、日志脱敏和外部副作用是否安全
- 测试是否通过真实入口保护行为，fixture 与 test double 是否越过被测边界
- prompt-doc 是否把事实放在正确 Owner，链接与代码行为是否一致

风格问题只有在影响正确性、维护边界或违反项目强制规范时才作为发现报告。

## 输出要求

先给出按严重性排序的可操作发现。每项包含精确文件与行、触发条件、实际影响、证据和最小修复方向；不要只写抽象担忧。没有发现时明确说明，并列出已检查范围和残余验证风险。

评审本身不修改代码、不暂存、不提交，也不把无关工作区改动归入当前任务。需要修复时按发现类型交给 `project-code-implement`、`project-test-verification`、`project-docs-helper` 或 `project-deploy-build`。
