# 类型建模

类型应表达目标仓库真实的数据层级、ownership 和失败契约，不追求抽象形式上的统一

## 事实源

先读目标仓库的公开类型、调用边界、agent instructions 和直接相关设计。通用建议不能覆盖已经明确的领域模型和生命周期

## interface、type 和 class

| 形态 | 使用 |
|---|---|
| `interface` | 需要扩展或实现的对象契约、依赖端口和清晰对象形状 |
| `type` | union、intersection、tuple、函数签名、映射和别名 |
| `class` | 有运行时实例身份、行为、状态或资源生命周期 |

对象形状可以按局部一致性使用 interface 或 type，不为转换形式制造无行为 diff。Record、索引签名和工具类型按 key 约束与可读性选择，不设绝对禁令

## 不可信输入

- 外部输入、JSON、SDK 返回和反序列化结果优先从 `unknown` 开始
- 在边界使用现有 schema、类型守卫或显式检查收窄
- 第三方限制迫使使用 `any` 时把范围压到最小并说明原因
- 避免双重断言和用非空断言掩盖生命周期问题

## 联合和泛型

闭集状态和结果优先使用字符串字面量或 discriminated union。enum 只在运行时对象或现有协议需要时使用，并跟随相邻代码

泛型只在调用方确实保留类型关系时使用，添加必要约束；类型参数只出现一次通常可以改为具体边界类型

## 缺失值

以当前 `tsconfig.json` 的 strict 和 null 检查选项为准，不假装编译器提供未启用的安全保证，也不在普通任务中擅自开启严格选项。新增或修改边界仍应显式处理 `undefined` 和协议规定的 `null`

## 对象关系

包含、实现和继承只按真实结构实现。两个对象共同服务一个功能不需要额外 interface、handle 或 wrapper
